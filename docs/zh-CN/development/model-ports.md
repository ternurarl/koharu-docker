# 模型移植

Koharu 以 Rust 对着固定版本的检查点重写上游模型。只有在相同输入上复现参考实现，移植才算正确；输出看着合理不构成证据。

本页记录如何验证移植，以及会产生「自信的错误答案」的失败模式。

## 必须对齐什么

影响检查点的结构必须精确对齐：变量名与嵌套关系、哪些层带偏置、归一化的 eps、激活函数变体（`gelu("none")` 与 `gelu("tanh")` 是不同的）。以发布的 `model.safetensors` 头部为准，不要相信指南或模块文档注释：

```bash
python -c "import json,struct; f=open('model.safetensors','rb'); n=struct.unpack('<Q',f.read(8))[0]; h=json.loads(f.read(n)); print([k for k in h if 'projector' in k])"
```

书面迁移指南在检查点能定论的细节上可能出错。Hayai Nova 移植中，指南写了一个发布检查点并不存在的线性偏置开关，还用了一个 `koharu-torch` 里根本没有的 `Path` 构造字段。检查点才是权威。

`VarStore::load` 遍历已注册的变量，缺少就报错，但会忽略文件里多出来的键。因此训练期的辅助分类头是无害的，不需要注册占位层。

## 对照参考实现验证

比对中间张量，不要只看最终文本。输出差一个 token 几乎不说明问题；数值首次发散的那一层才指明缺陷在哪。

1. 把 Rust 侧每个阶段导出为 `.npy`：预处理后的像素、编码器输出、投影器输出、RoPE 表、prefill 隐状态、逐步 logits。
2. 把同一批张量载入参考实现，逐层比对。
3. 看每一层的数量级：fp32 路径上 `1e-3` 的相对误差是舍入，`1e-1` 是缺陷。

### 先隔离预处理，再怪模型

最有判别力的一个测试：把**我们**预处理出的像素喂给参考实现的生成流程。若参考实现也复现了我们的错误输出，差异在预处理；若参考实现仍然正确，差异就在移植内部。

在对架构做任何推理之前先做这一步。Hayai 移植中，对着注意力掩码和 RoPE 网格推理了半天毫无收获，而这一个测试干净利落地把问题一分为二，直指视觉编码器。

### 把有效位置和填充分开

填充行通常会被后续阶段丢弃。有效区域和填充区域要分别比对，否则填充噪声会主导汇总统计，掩盖掉真正重要位置上的发散。`max_abs` 远大于 `mean_abs` 就是「少数几行有问题」的特征——先查清是哪几行，再下任何结论。

## 失败模式

### 未经核实就断言限制的注释

注释声称某个绑定不暴露某项操作，这只是一种说法，不是事实。Hayai 移植带着一条注释，说 LibTorch 不暴露抗锯齿双线性缩放。它其实暴露了（`internal_upsample_bilinear2d_aa`，正是 `F.interpolate(..., antialias=True)` 背后的核）。

同一条注释还断言在 16x16 源网格上差异可忽略。这在升采样轴上成立，在降采样轴上不成立——而抗锯齿恰恰只影响降采样，也就是说这个断言在唯一要紧的场景下是错的：

| patch 网格 | 有无抗锯齿的相对差异 |
| --- | ---: |
| 23x23（升采样） | 1e-07 |
| 7x36（降采样） | 0.32 |
| 4x18（降采样） | 0.54 |

「可忽略」的断言要在负载真正产生的场景下验证，不要挑一个容易推理的场景了事。

### 把每次发散都当成缺陷

发布的基准指标给出了模型能力的上限。一个声称精确命中 75% 的发布，就是在告诉你每四张裁切图里有一张不会逐字命中；单张 fixture 上翻转一个标点落在这个包络之内，本身不构成移植错误的证据。

反过来，也不要拿这个包络去解释系统性差异。判别方法是看参考实现能否在相同输入上复现同样的结果。

### 把参考实现当成规范

参考实现是代码，代码会携带产物。Hayai 发布的归一化用单次 Python `re.sub` 剥离 CJK 字符之间的空白，而 `re.sub` 是非重叠扫描，于是在一串 CJK 词之间会留下交替的空格：

```
"あ い う え"  ->  "あい うえ"    # 发布流水线的行为
"あ い う え"  ->  "あいうえ"    # 注释宣称的行为
```

当行为与宣称的意图不一致时，要主动取舍并把选择写进注释。目标是基准对齐就复现该产物；目标是输出质量就修掉它。Hayai 移植选择了全部剥离，因为下游翻译需要空格消失。

### 手抄测试用例

为了让 Rust 测试对上 Python 字面量而手写 `\u{...}` 转义，是发明幻觉缺陷的可靠办法。这次移植里 Rust 用例和 Python 用例差了两个码点，于是产生了一处假的不匹配，看起来像 Unicode 规范化器坏了，排除它花掉了不少时间。

把用例列表写到一个共享文件里，两边都从它读取。用转义后的输出做程序化比对，绝不要靠肉眼看控制台文本。

## 工具链陷阱

- **过期的二进制。** `cargo test` 只重建库，不会重建先前编译过的 `target/debug/<bin>`。改动对 CLI 输出毫无效果时，通常只是二进制旧了。下结论说修复失败之前先重建 bin。
- **Windows 控制台编码。** UTF-8 结果经非 UTF-8 控制台管道传输，或进入假定某种编码的脚本，会显示出数据里并不存在的替换字符。把结果写入文件再比对，报告时用 `ascii()` 或十六进制码点。
- **Python 隔离选项。** `-I` 会剔除 user site-packages，于是用 `--user` 装的包看起来像不存在。处理不可信输入时若仍需这些包，改用 `-E`。
- **路径写法。** Windows Python 不认 `/d/...` 这种 Git Bash 路径，要用盘符路径。

## 本地检查点

把固定版本的检查点放进运行时存储，`resolve()` 就会直接命中而不再下载：

```
<store>/hugging-face/models/<owner>--<repo>/snapshots/<revision>/<file>
```

存储根目录是 `dirs::cache_dir()/koharu/packages`；若宿主配置了数据目录，则是该目录下的 packages。当目标已是文件时，`HuggingFaceFile::resolve` 会提前返回。

## 检查清单

- 读检查点头部，对齐名称、偏置、eps 与激活函数。
- 把我们预处理出的输入喂给参考实现，以隔离预处理与模型本身。
- 逐层比对中间张量，有效位置与填充分开处理。
- 从发布说明复现参考实现的后处理契约，不要只看它的代码。
- 判定修复是否生效之前先重建二进制。
- 提交前删除临时导出代码。
