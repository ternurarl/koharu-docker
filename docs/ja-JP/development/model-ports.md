# モデル移植

Koharu は Rust で、ピン留めされたチェックポイントに対して上流モデルを書き直します。移植が正しいのは、同一入力でリファレンス実装を再現したときだけで、もっともらしい出力は証拠になりません。

このページでは移植の検証方法と、「自信を持った誤答」を生む失敗パターンを記録します。

## 合わせるべきもの

チェックポイントに影響する構造は正確に合わせる必要があります。変数名とネスト関係、どの層がバイアスを持つか、正規化の eps、活性化関数のバリアント（`gelu("none")` と `gelu("tanh")` は別物です）。ガイドやモジュールのドキュメントコメントではなく、公開された `model.safetensors` のヘッダーを典拠にしてください。

```bash
python -c "import json,struct; f=open('model.safetensors','rb'); n=struct.unpack('<Q',f.read(8))[0]; h=json.loads(f.read(n)); print([k for k in h if 'projector' in k])"
```

書き上げられた移行ガイドは、チェックポイントが決められる細部で誤りを含むことがあります。Hayai Nova の移植では、ガイドは公開チェックポイントに存在しない線形バイアスの切替を記述し、`koharu-torch` に存在しない `Path` 構造フィールドを使っていました。権威はチェックポイントです。

`VarStore::load` は登録済みの変数をたどり、ファイルに欠けていればエラーにしますが、ファイルに余分なキーは無視します。そのため訓練時の補助分類ヘッドは無害で、プレースホルダー層を登録する必要はありません。

## リファレンス実装と照合する

中間テンソルを比較してください。最終テキストだけではありません。出力が 1 トークン違うだけではほとんど何も分からず、値が最初に発散した層が欠陥の場所を教えてくれます。

1. Rust 側の各段階を `.npy` に書き出します。前処理後のピクセル、エンコーダー出力、プロジェクター出力、RoPE テーブル、prefill 隠れ状態、ステップごとの logits です。
2. 同じテンソル群をリファレンス実装に読み込み、層ごとに比較します。
3. 各層の桁を見ます。fp32 経路上の `1e-3` の相対誤差は丸め誤差、`1e-1` は欠陥です。

### まず前処理を分離してからモデルを疑う

判別力が最も高いテストは、**私たち**が前処理したピクセルをリファレンス実装の生成フローに与えることです。リファレンス実装も私たちと同じ誤った出力を再現するなら、差分は前処理にあります。リファレンス実装が正しければ、差分は移植の内部にあります。

アーキテクチャについて推論する前に、まずこのステップを行ってください。Hayai 移植では、アテンションマスクと RoPE グリッドを巡る推論はまったく実りがなく、このテストが問題をきれいに二分し、視覚エンコーダーを直接指し示しました。

### 有効位置とパディングを分ける

パディング行は通常、後続の段階で破棄されます。有効領域とパディング領域は別々に比較してください。さもないとパディングのノイズが要約統計を支配し、本当に重要な位置の発散を隠してしまいます。`max_abs` が `mean_abs` よりずっと大きいのは「一部の行に問題がある」特徴です。まずどの行かを突き止めてから、いかなる結論も下さないでください。

## 失敗パターン

### 未検証の制限を断言するコメント

あるバインディングが操作を公開していないというコメントは、主張であって事実ではありません。Hayai 移植には、LibTorch がアンチエイリアス付き双線形拡大縮小を公開していないというコメントが付いていました。実際には公開されており（`internal_upsample_bilinear2d_aa`、`F.interpolate(..., antialias=True)` の背後にあるまさにそのカーネルです）。

同じコメントは、16x16 のソースグリッド上なら差は無視できるとも断言していました。これはアップサンプリング軸では成り立ちますが、ダウンサンプリング軸では成り立ちません。アンチエイリアスはダウンサンプリングにだけ影響するため、この断言は唯一重要な場面で間違えています。

| patch グリッド | アンチエイリアス有無の相対差 |
| --- | ---: |
| 23x23（アップサンプリング） | 1e-07 |
| 7x36（ダウンサンプリング） | 0.32 |
| 4x18（ダウンサンプリング） | 0.54 |

「無視できる」という断言は、負荷が実際に生み出す場面で検証してください。推論しやすい場面を選んで済ませてはいけません。

### 発散のたびにバグと決めつけない

公開ベンチマークはモデル能力の上限を示します。正確一致 75% を謳うリリースは、4 枚のクロップに 1 枚は逐語一致しないことを意味しています。単一 fixture で句読点 1 つが反転するのはこの包絡の内側であり、それ自体は移植誤りの証拠になりません。

逆に、その包絡で系統的な差を正当化してはいけません。判別方法は、同じ入力でリファレンス実装が同じ結果を再現できるかを見ることです。

### リファレンス実装を仕様とみなす

リファレンス実装はコードであり、コードは産物を抱えています。Hayai 公開の正規化は単発の Python `re.sub` で CJK 文字間の空白を取り除きますが、`re.sub` は非重複スキャンなので、CJK 語の並びには交互の空白が残ります。

```
"あ い う え"  ->  "あい うえ"    # 公開パイプラインの挙動
"あ い う え"  ->  "あいうえ"    # コメントが主張する挙動
```

挙動が意図と食い違うときは、意図的に取捨選択を決めてコメントに書いてください。ベンチマーク整合が目標なら産物を再現し、出力品質が目標なら修正します。Hayai 移植は全除去を選びました。下流翻訳には空白が無いことが必要だからです。

### テストケースの手写し

Rust テストを Python のリテラルに合わせるために `\u{...}` エスケープを手で書くと、幻のバグを確実に生み出します。今回の移植では Rust と Python のケースが 2 コードポイントずれ、Unicode 正規化器が壊れているように見える偽の不一致が生じました。排除にかなりの時間を費やしました。

ケースのリストを共有ファイルに書き、両側からそれを読ませてください。エスケープ済みの出力でプログラム的に比較し、コンソールのテキストを目視に頼ってはいけません。

## ツールチェーンの落とし穴

- **古いバイナリ。** `cargo test` はライブラリだけを再ビルドし、以前ビルドした `target/debug/<bin>` は再ビルドしません。変更が CLI 出力にまったく効かないときは、まず bin を再ビルドしてください。
- **Windows のコンソールエンコーディング。** UTF-8 の結果を非 UTF-8 コンソールのパイプに通すと、データに存在しない置換文字が表示されます。結果をファイルに書いて比較してください。
- **Python の分離フラグ。** `-I` は user site-packages を取り除くので、`--user` でインストールしたパッケージが無いように見えます。信頼できない入力を扱いつつそれらのパッケージが必要な場合は `-E` に切り替えてください。
- **パスの書き方。** Windows の Python は `/d/...` のような Git Bash パスを解決できません。ドライブレターのパスを使ってください。

## ローカルチェックポイント

ピン留めしたチェックポイントをランタイムストアに置けば、`resolve()` がダウンロードなしで直接ヒットします。

```
<store>/hugging-face/models/<owner>--<repo>/snapshots/<revision>/<file>
```

ストアのルートディレクトリは `dirs::cache_dir()/koharu/packages` です。ホストがデータディレクトリを設定している場合は、そのディレクトリ下の packages です。対象がすでにファイルの場合、`HuggingFaceFile::resolve` は早期に返します。

## チェックリスト

- チェックポイントのヘッダーを読み、名前、バイアス、eps、活性化関数を合わせる。
- 前処理済み入力をリファレンス実装に与え、前処理とモデル自体を分離する。
- 中間テンソルを層ごとに比較し、有効位置とパディングは分けて扱う。
- リファレンス実装の後処理契約は、そのコードだけでなくリリースノートから再現する。
- 修正が効いたか判断する前にバイナリを再ビルドする。
- コミット前に一時的なダンプコードを削除する。
